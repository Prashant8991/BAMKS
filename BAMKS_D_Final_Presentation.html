BAMKS-D

Blockchain-Assisted Multi-Keyword Searchable Encryption
with Dynamic Document Operations for Healthcare Cloud

Based on: Cheng et al., Elsevier Internet of Things, 2026
Technology Stack: AES-256-GCM · CP-ABE · Ethereum Smart Contracts · SNIZK Proofs

🔒 Secure · ⚡ Efficient · 🔗 Decentralized

Aim & Objectives

🎯

Primary Aim

Design a secure, searchable, and dynamically updatable healthcare data management system that enables hospitals to encrypt and store patient records on the cloud while allowing authorized doctors to search and retrieve them — without the cloud server ever seeing plaintext data.

📋

Key Objectives

  • Encrypt EHR records using AES-256-GCM
  • Enable multi-keyword searchable encryption
  • Support O(m) single-document addition
  • Achieve O(1) instant revocation via blockchain
  • Enforce CP-ABE attribute-based access control
  • Verify data integrity with SNIZK proofs

Research Gap

⚠️

Problems in Existing Systems

  • Static Datasets: No support for adding/removing documents after initial setup
  • Expensive Revocation: Revoking 1 document requires re-encrypting ALL documents → O(L×m)
  • No Blockchain Audit: No tamper-proof verification of document status
  • Single-keyword Only: Most schemes support only single-keyword search
  • Weak Access Control: No fine-grained attribute-based policies
✅

How BAMKS-D Solves These

  • Dynamic Operations: Add single document in O(m) without re-building entire index
  • O(1) Revocation: Single blockchain flag flip instead of full re-keying
  • Blockchain Audit Trail: Immutable on-chain record of all document operations
  • Multi-keyword Search: Bilinear pairing-based conjunctive keyword matching
  • CP-ABE Access: Only users with matching attributes can decrypt
Core Innovation: BAMKS-D is the first system to combine multi-keyword searchable encryption with O(1) blockchain-based revocation and CP-ABE access control for healthcare cloud data.

System Architecture

Four-entity architecture: Hospital (Data Owner), Cloud Server (Off-Chain), Ethereum Blockchain (On-Chain), Doctor (Data User)

Methodology — Encryption & Upload Flow

Step-by-Step Process

  • Step 1: Hospital generates a random 256-bit AES key (σk)
  • Step 2: Record encrypted with AES-256-GCM → produces ciphertext + 96-bit nonce + 128-bit GCM tag
  • Step 3: Document tag yk = gσk mod P generated
  • Step 4: Keyword index tokens built: gη·H1(kw)

Parallel Operations

  • 🔵 To Cloud: Encrypted payload + keyword index uploaded
  • 🟢 To Blockchain: Document tag yk + docId registered on smart contract

Methodology — Search & Decryption Flow

Search Phase

  • Doctor generates trapdoor tokens (T1, T2, T3) using CP-ABE secret key
  • Cloud performs bilinear pairing match:
    e(T1,C1)·e(T2,C2) = e(T3,C3)?
  • Matching records identified without decrypting any data

Blockchain Verification + Decrypt

  • Check deletedDocRegistry[docId] on blockchain → O(1)
  • If active → decrypt with AES-256-GCM using key σk
  • Verify SNIZK proof to confirm data integrity
  • If revoked → access blocked immediately

Algorithms Used

🔐

AES-256-GCM

Role: Symmetric encryption of EHR records

Why GCM? Provides both confidentiality AND integrity in one pass. The 128-bit GCM tag detects any tampering.

256-bit key 96-bit nonce 128-bit tag
🔑

CP-ABE

Role: Attribute-based access control

How: Ciphertext is bound to a policy (e.g., "Dept=Cardiology AND Role=Doctor"). Only users whose attributes satisfy the policy can decrypt.

Policy-based Fine-grained
⛓️

Ethereum Smart Contract

Role: On-chain document registry & O(1) revocation

How: BAMKS_Registry.sol stores docId → yk mappings and deletedDocRegistry boolean flags.

Solidity Immutable
🔍

Bilinear Pairing Search

Role: Multi-keyword searchable encryption

Uses Type-3 pairings on elliptic curves for conjunctive keyword matching over encrypted data.

e(G₁,G₂)→G_T Trapdoor
🛡️

SNIZK Proofs

Role: Data integrity verification

Succinct Non-Interactive Zero-Knowledge proofs verify that returned data hasn't been tampered without revealing the data itself.

Zero-Knowledge Non-Interactive
📊

Inverted Keyword Index

Role: Efficient document lookup

Maps encrypted keyword tokens to document IDs, enabling O(n) search over n documents without scanning all records.

O(n) search Dynamic

Blockchain Architecture — On-Chain vs Off-Chain

On-chain stores lightweight metadata (docId, tag, status); Off-chain stores heavy encrypted payloads — linked by docId

CP-ABE Access Control Mechanism

Policy tree enforces fine-grained access — only users with ALL required attributes can decrypt the ciphertext

O(1) Revocation Mechanism

BAMKS-D achieves 46,000× faster revocation by using on-chain boolean flags instead of expensive full re-keying

Key Features & Innovations

⚡

O(m) Single-Doc Addition

Add one document without rebuilding the entire index. Only m keyword tokens need to be generated for the new document.

🚀

O(1) Instant Revocation

Revoke a document by flipping a single boolean on the blockchain. No re-encryption, no key re-issue.

🔒

End-to-End Encryption

Cloud server never sees plaintext. AES-256-GCM encrypts data; CP-ABE controls who can decrypt.

🔍

Multi-Keyword Search

Search across multiple keywords simultaneously using bilinear pairing-based trapdoors over encrypted data.

🛡️

Tamper-Proof Audit

Every document operation is recorded on the Ethereum blockchain — creating an immutable audit trail.

✅

SNIZK Integrity

Zero-knowledge proofs verify data hasn't been modified without revealing the data itself to the verifier.
