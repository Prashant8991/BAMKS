\begin{abstract}
In cloud-edge IoT architectures for healthcare, sharing encrypted Electronic Health Records (EHR) demands fine-grained access control, conjunctive keyword search, and verifiable query results. The BAMKS scheme (Cheng et al., \textit{Internet of Things}, 2026) addressed multi-authority access control and blockchain result verification, yet its index update mechanism requires either re-indexing the entire collection or executing $O(L \cdot m)$ group updates across all existing documents. In this paper, we present BAMKS-D, an algorithmic prototype and architecture integration layer that introduces atomic file-level operations. Single-document addition operates in strict $O(m)$ time, achieving a \textbf{12.11$\times$ speedup} at $L=5,000$ files over Cheng et al. Section 5.10 index updates (and 3,527.7$\times$ over naive full re-encryption). Single-document revocation is mapped directly to Ethereum Virtual Machine (EVM) storage (\texttt{mapping(uint256 => bool) deletedDocRegistry}), achieving $O(1)$ constant-time lookup with zero array traversal. We validate the architecture through live smart contract deployment on the Ethereum Sepolia Testnet (\texttt{0xfDC8615Bf6483c3B0f39c330F55A56Cb0f08C8D3}), decentralized IPFS storage, and a 30-run empirical benchmark ($m=3$). An honest assessment of prototype algebraic assumptions, inverted index access-pattern leakage, and threats to validity is presented.
\end{abstract}

\section{Introduction}

The proliferation of Internet of Medical Things (IoMT) devices—such as wireless cardiac monitors, ambulatory pulse oximeters, and bedside telemetry sensors—has transformed contemporary healthcare delivery \cite{gupta2023security, dhinakaran2025safeguarding}. Modern medical facilities generate voluminous streams of Electronic Health Records (EHR) that must be archived securely in external Cloud Storage Providers (CSP) while preserving clinician query capabilities. Because medical data contains sensitive diagnostic diagnoses protected under regulatory statutes (e.g., HIPAA and GDPR), plaintexts must be encrypted under fine-grained access policies before outsourcing \cite{janarthanan2024privacy}.

To reconcile cryptographic confidentiality with expressive querying, Ciphertext-Policy Attribute-Based Keyword Search (CP-ABKS) schemes were formulated \cite{boneh2004peks, bethencourt2007cpabe}. In CP-ABKS, data owners encrypt documents under an access structure (e.g., $(\text{Role\_Doctor} \land \text{Dept\_Cardiology})$), and only clinicians with valid attribute credentials can generate search trapdoors or decrypt returned records \cite{sahai2005fuzzy, waters2011expressive}. Recently, Cheng et al. \cite{cheng2026bamks} proposed BAMKS, introducing decentralized multi-authority key generation, multi-owner collaborative indexing, and a blockchain Result Verification Smart Contract (RVSC) utilizing aggregated Schnorr Non-Interactive Zero-Knowledge (SNIZK) proofs \cite{schnorr1991}.

\textbf{The Open Challenge in BAMKS:} In Section 8 of their foundational paper, Cheng et al. identified a critical operational bottleneck \cite{cheng2026bamks}: their architecture supports dynamic user credential updates, but does not provide an efficient mechanism for single-file additions or deletions. Adding a single document requires either re-encrypting and re-indexing the entire document collection (naive baseline), or updating the entire inverted index via modular multiplication of an update token $X_{upd}$ across all $L \cdot m$ index entries (Section 5.10 baseline) \cite{cheng2026bamks}. For an enterprise healthcare repository with $L = 5,000$ records and $m = 3$ keywords, updating 15,000 index entries introduces noticeable latency. Furthermore, document deletion in prior schemes requires either re-encrypting the remaining corpus or relying on cloud server honesty.

\textbf{Contributions:} In this work, we propose \textbf{BAMKS-D}, an architecture integration and dynamic evaluation framework that addresses these limitations:
\begin{itemize}
    \item \textbf{Atomic Single-Document Addition ($O(m)$):} We decouple the inverted keyword index so that appending a new EHR requires generating ciphertexts and index tokens for only the $m$ keywords of that specific file, eliminating collection-wide re-indexing.
    \item \textbf{Instant On-Chain Document Revocation ($O(1)$):} We formulate an EVM state mapping mechanism (\texttt{deletedDocRegistry}) that executes in constant time via \texttt{keccak256} direct slot addressing, avoiding iterative blockchain array traversal.
    \item \textbf{Live Ethereum Sepolia Deployment:} We deploy and verify \texttt{BAMKS\_Registry.sol} on the public Ethereum Sepolia Testnet (\texttt{0xfDC8615Bf6483c3B0f39c330F55A56Cb0f08C8D3}), reporting receipt-based gas consumption and confirmation times.
    \item \textbf{Rigorous Fair Benchmarks (30 Runs):} We evaluate BAMKS-D against both naive re-encryption and the true Cheng et al. Section 5.10 index update baseline, demonstrating a \textbf{12.11$\times$ speedup} at $L=5,000$ files on an Intel Core i5-13420H platform.
\end{itemize}

\section{Related Work}

Public-Key Encryption with Keyword Search (PEKS) was introduced by Boneh et al. \cite{boneh2004peks}, enabling untrusted servers to evaluate keyword matches. However, basic PEKS was limited to single keywords and vulnerable to Keyword Guessing Attacks (KGA). Sahai and Waters \cite{sahai2005fuzzy} formulated Attribute-Based Encryption (ABE), which Bethencourt et al. \cite{bethencourt2007cpabe} extended to Ciphertext-Policy ABE (CP-ABE). Waters \cite{waters2011expressive} formalized expressive CP-ABE using Linear Secret Sharing Schemes (LSSS). Dynamic Searchable Symmetric Encryption (DSSE) was explored by Song et al. \cite{song2000practical}, Curtmola et al. \cite{curtmola2011searchable}, Kamara et al. \cite{kamara2012dynamic}, and Bost \cite{bost2016sophos}, establishing forward and backward security notions for symmetric settings.

In attribute-based search, Li et al. \cite{li2021verifiable} developed verifiable data sharing with outsourced decryption, while Zhang et al. \cite{zhang2022subversion} investigated subversion-resistant search over cloud storage. Multi-authority architectures were analyzed by Chase \cite{chase2007multi} and Lewko and Waters \cite{lewko2010multiauthority}. Predicate encryption schemes supporting inner-product matching were proposed by Katz, Sahai, and Waters \cite{katz2013predicate}. Broadcast encryption techniques were studied by Delerabl\'ee et al. \cite{delerablee2007dynamic}. Blockchain-assisted searchable encryption was explored by Yang et al. \cite{yang2022blockchain}, Sun et al. \cite{sun2021privacy}, and Cheng et al. \cite{cheng2026bamks}, using smart contracts on Ethereum \cite{wood2024ethereum} and decentralized IPFS storage \cite{benet2014ipfs}. \section{Preliminaries \& System Model}

\subsection{Prototype Algebraic Setting}
In our software prototype, algebraic computations are evaluated in the multiplicative group $(\mathbb{Z}_P^*, \cdot)$ using the 256-bit prime $P = 2^{256} - 2^{32} - 977$ (the secp256k1 field prime), with generator $g = 2$. We explicitly note that $\mathbb{Z}_P^*$ has composite order $P-1$ and does not support bilinear pairings; pairings $e(g_1, g_2)$ are evaluated via modular exponentiation for prototype simulation. Cryptographic hash functions include $H_1: \{0,1\}^* \to \mathbb{Z}_P^*$ and $H_2: \{0,1\}^* \to \{0,1\}^{256}$ (SHA-256).
\begin{equation}
P = 2^{256} - 2^{32} - 977
\end{equation}

\subsection{Entities and Threat Model}
BAMKS-D operates across seven entities: (1) \textbf{Key Generation Center (KGC)} initializing global parameters ($GP$), (2) \textbf{Attribute Authorities ($AA$)} managing disjoint clinical attribute universes, (3) \textbf{Data Owners ($DO$)} encrypting EHRs and pinning payloads to IPFS, (4) \textbf{Data Users ($DU$)} submitting trapdoors, (5) \textbf{Cloud Service Provider ($CSP$)} indexing tokens and matching queries, (6) \textbf{Ethereum Sepolia Smart Contract} maintaining revocation state, and (7) \textbf{IPFS} decentralized content-addressed storage.

The CSP is modeled as \textit{honest-but-curious}: it executes search algorithms correctly but attempts to correlate queries and infer keyword patterns. Data Users may attempt attribute collusion. The blockchain provides a tamper-proof state execution layer.

\section{The Proposed BAMKS-D Protocol}

\subsection{Key Generation with Session Randomness}
To prevent key correlation across distinct issuances, each KeyGen invocation samples fresh per-generation session randomness $t \in_R \mathbb{Z}_{P-1}^*$:
\begin{equation}
K_1 = H_1(uid)^{-t \pmod{P-1}} \pmod P
\end{equation}
\begin{equation}
K_{2,i} = \left( H_1(uid)^{t \cdot \beta_i} \cdot dpk_{ver}^{\alpha_i} \right) \pmod P
\end{equation}

\subsection{Atomic Single-Document Addition}
When an EHR document $docId$ with $m$ keywords $W_{doc} = \{w_1, \dots, w_m\}$ is created, the owner generates an AES key via $KDF(\Phi, verId)$, encrypts the file payload with AES-256-GCM, uploads the ciphertext to IPFS, and computes keyword tokens only for $W_{doc}$:
\begin{equation}
I_{doc,j} = g^{(\eta \cdot H_1(w_j)) \pmod{P-1}} \pmod P
\end{equation}
The CSP appends $Index_{doc}$ to the global inverted index without modifying any existing document tokens, achieving strict $O(m)$ complexity (Algorithm~\ref{alg:add}).

\begin{algorithm}[htbp]
\caption{SingleDocAdd($docId, F, W_{doc}, \Phi, verId$)}
\label{alg:add}
\begin{algorithmic}[1]
\REQUIRE Document identifier $docId$, payload $F$, keyword set $W_{doc}$, collaborative secret $\Phi$, version $verId$.
\ENSURE Uploaded CID, local index $Index_{doc}$, public tag $y_k$.
\STATE $K \leftarrow KDF(\Phi, verId)$; $C_{data} \leftarrow \text{AES-GCM-Enc}(K, F)$
\STATE $CID \leftarrow \text{IPFS.upload}(C_{data})$; $y_k \leftarrow g^{\sigma_k} \pmod P$
\STATE Initialize $Index_{doc} \leftarrow \emptyset$
\FORALL{$w_j \in W_{doc}$}
    \STATE $I_{doc,j} \leftarrow g^{(\eta \cdot H_1(w_j)) \pmod{P-1}} \pmod P$
    \STATE $Key_j \leftarrow H_2(\text{'tok\_'} \parallel I_{doc,j})$
    \STATE $Index_{doc}[Key_j] \leftarrow I_{doc,j}$
\ENDFOR
\STATE Execute on-chain transaction: $\texttt{registerDocument}(docId, H_2(C_{data}), y_k)$
\STATE \textbf{return} $(CID, Index_{doc}, y_k)$
\end{algorithmic}
\end{algorithm}

\subsection{On-Chain Single-Document Revocation}
Revoking a document executes on-chain via Algorithm~\ref{alg:del}, updating the mapping storage directly.

\begin{algorithm}[htbp]
\caption{SingleDocDelete($docId$) [On-Chain EVM]}
\label{alg:del}
\begin{algorithmic}[1]
\REQUIRE Document identifier $docId$, transaction sender $msg.sender$.
\ENSURE Document revoked in EVM state, emitting \texttt{DocumentDeleted}.
\STATE \textbf{require} $\texttt{fileRegistry}[docId].\text{ownerAddress} == msg.sender$
\STATE \textbf{require} $!\texttt{deletedDocRegistry}[docId]$
\STATE $slot \leftarrow \text{keccak256}(\text{abi.encode}(docId, slotNumber))$
\STATE $\texttt{deletedDocRegistry}[docId] \leftarrow \text{true}$
\STATE $\texttt{fileRegistry}[docId].\text{isDeleted} \leftarrow \text{true}$
\STATE \textbf{emit} $\texttt{DocumentDeleted}(docId, msg.sender, block.timestamp)$
\STATE \textbf{return} $\text{true}$
\end{algorithmic}
\end{algorithm}

\subsection{Conjunctive Keyword Search}
A clinician querying keywords $\widetilde{W} = \{\widetilde{w}_1, \dots, \widetilde{w}_q\}$ generates trapdoor tokens:
\begin{equation}
T_1 = g^\phi \pmod P, \quad T_3 = g^{(\phi \sum H_1(\widetilde{w}_j)) \pmod{P-1}} \pmod P
\end{equation}
The CSP verifies matches for active documents via Algorithm~\ref{alg:search}:
\begin{equation}
(I_{prod})^\phi \equiv (T_3)^\eta \equiv g^{(\eta \phi \sum H_1(\widetilde{w}_j)) \pmod{P-1}} \pmod P
\end{equation}

\begin{algorithm}[htbp]
\caption{ConjunctiveSearch($Trap, Index, deletedRegistry$)}
\label{alg:search}
\begin{algorithmic}[1]
\REQUIRE Trapdoor $Trap$, Cloud Index $Index$, On-chain deletion registry.
\ENSURE Search Result List $SRL$.
\STATE $SRL \leftarrow \emptyset$
\FORALL{$docId \in Index_W$}
    \IF{$deletedRegistry[docId] == \text{true}$}
        \STATE \textbf{continue}
    \ENDIF
    \IF{all query tokens present in $Index_W[docId]$}
        \STATE $I_{prod} \leftarrow \prod I_{doc,j} \pmod P$
        \IF{$(I_{prod})^\phi \equiv (T_3)^\eta \pmod P$}
            \STATE $SRL \leftarrow SRL \cup \{docId\}$
        \ENDIF
    \ENDIF
\ENDFOR
\STATE \textbf{return} $SRL$
\end{algorithmic}
\end{algorithm}

\begin{algorithm}[htbp]
\caption{AggregatedSchnorrNIZKVerify($SRL, \{y_k\}, \hat{\pi}, R$)}
\label{alg:nizk}
\begin{algorithmic}[1]
\REQUIRE Result list $SRL$, public tags $\{y_k\}$, aggregated proof $(\hat{\pi}, R)$.
\ENSURE Verification decision (Accept / Reject).
\STATE $RHS \leftarrow g^{\hat{\pi}} \pmod P$
\FORALL{$k \in SRL$}
    \STATE $h_k^* \leftarrow H_1(y_k^* \parallel R)$; $RHS \leftarrow RHS \cdot (y_k^*)^{-h_k^*} \pmod P$
\ENDFOR
\IF{$R == RHS$}
    \STATE \textbf{return} Accept
\ELSE
    \STATE \textbf{return} Reject
\ENDIF
\end{algorithmic}
\end{algorithm}

\subsection{Comparative Discussion}
For small datasets ($L \le 100$), Cheng et al. Section 5.10 index update is faster ($0.02\text{--}0.16$\,ms) because updating a few dozen tokens via modular multiplication incurs less overhead than AES-GCM file encryption. However, because Cheng et al. scales linearly as $O(L \cdot m)$, the break-even crossover occurs at $L \approx 300$ documents (via linear interpolation between $L=100$ and $L=500$) and asymptotically at $L \approx 410$ against the $L=5,000$ measurement ($0.67$\,ms). At $L=5,000$, BAMKS-D addition remains flat ($0.67$\,ms), delivering a \textbf{12.11$\times$ speedup} over Cheng et al. and a \textbf{3,527.7$\times$ speedup} over naive full re-encryption ($2,363$\,ms).

Index storage scales strictly linearly: 4,098 bytes for the 8 baseline records (512.2 B/doc including schema metadata), with 10 added records consuming 4,520 bytes (452.0 B/doc).

\section{Limitations \& Threats to Validity}

To ensure complete academic transparency, we explicitly document the prototype limitations of this study:
\begin{itemize}
    \item \textbf{Simulated Group Algebra:} Field operations are evaluated in $(\mathbb{Z}_P^*, \cdot)$ using $P = 2^{256} - 2^{32} - 977$. This group has order $P-1$ (composite) and does not possess a bilinear map. Formal pairing-based security reductions (e.g., DBDH) require porting to a Type-III pairing curve (e.g., BN254 or BLS12-381 via Charm-Crypto or pypairing).
    \item \textbf{Prototype CSP Separation:} In the software prototype demonstration script, the CSP search function receives group parameters $\eta$ and $\phi$ directly to test match equations. In a production deployment, bilinear pairings are required to evaluate matching without disclosing secrets.
    \item \textbf{Access-Pattern \& Token Leakage:} Keyword tokens $I_{doc,j} = g^{\eta H_1(w_j)}$ are deterministic per keyword across documents. Consequently, an untrusted CSP can observe document frequency and search access patterns over time. Addressing access pattern leakage via Oblivious RAM (ORAM) or forward-private symmetric searchable encryption \cite{bost2016sophos} remains vital future work.
    \item \textbf{Simulated Policy Evaluation:} In the functional demonstration test suite, CP-ABE access policy satisfaction is evaluated via attribute set logic rather than an algebraic LSSS pairing engine.
    \item \textbf{Evaluation Dataset:} The empirical test suite utilizes 8 synthetic clinical records authored to model clinical formats (ECG, MRI, telemetry). Future work will evaluate production hospital corpora (e.g., MIMIC-IV or Enron email corpus).
    \item \textbf{Local vs. On-Chain Latency:} Local state flag updates take $< 0.001$\,ms in memory, whereas on-chain confirmation on Ethereum Sepolia requires block mining ($21.83$\,s confirmation for deletion; $35.22$\,s for registration).
\end{itemize}

\section{Conclusion}

This paper presented BAMKS-D, an algorithmic prototype and architecture integration layer addressing the dynamic file update challenge in blockchain-assisted ABKS. By decoupling inverted index generation, BAMKS-D achieves $O(m)$ single-file additions, yielding a 12.11$\times$ speedup over Cheng et al. Section 5.10 index updates at $L=5,000$ files (and 3,527.7$\times$ over naive re-encryption). On-chain revocation is enforced in $O(1)$ constant time via EVM mapping storage on Ethereum Sepolia. Future research will explore bilinear pairing integration on BN254 curves and forward-private multi-keyword search.
