PROJECT EVALUATION PRESENTATION

BAMKS-D: Secure Healthcare Cloud & Blockchain System

AIM: To design and implement a dynamic, fine-grained access control and searchable encryption architecture for cloud-edge-IoT healthcare environments that enables instant $\mathcal{O}(1)$ document revocation and $\mathcal{O}(m)$ single-file additions without re-encrypting the entire cloud database.

❌ 1. Base Paper Limitation (Cheng et al.)
  • Quote (Section 8, Page 22): "In the future, we plan to extend BAMKS to support dynamic adding, deleting, and updating."
  • The Bottleneck: Grouped all files into a static version $F_{\text{ver}}$.
  • Full Re-keying Drain: Modifying 1 file forced re-encryption of ALL $L$ files ($\mathcal{O}(L \cdot m)$ latency $\approx 5,560\text{ ms}$).
  • IoT Drain: Excessive CPU & battery consumption on edge devices.
✅ 2. Our Solved Research Extension
  • `SingleDocAdd` [$\mathcal{O}(m)$]: Appends 1 encrypted record without touch existing dataset ($\approx 0.12\text{ ms}$).
  • `SingleDocDelete` [$\mathcal{O}(1)$]: Flips smart contract revocation mapping `deletedDocRegistry[docId] = true` ($\approx 0.001\text{ ms}$).
  • `SingleDocModify` [$\mathcal{O}(m)$]: Deletes old record & appends new entry.
  • Result: 5.5 Million times faster deletion without dataset re-encryption!
⚙️ Core System Methodology

1. CP-ABE Access Control

Attribute-Based Encryption ties access policies (e.g. Role_Doctor AND Dept_Cardiology) to files. Attribute Authority issues secret keys $K_{2,x}$.

2. AES-256-GCM Payload

Symmetric encryption for patient plaintext. Uses a 96-bit random nonce for uniqueness and a 128-bit GCM tag for tamper detection.

3. Discrete Log Keyword Index

Encrypted index tokens $g^{\eta \cdot H_1(kw)} \bmod P$ hide keywords from the untrusted cloud while allowing trapdoor search matching.

📊 Upload Data Flowchart: Encryption vs. Blockchain Transaction

What happens when a Hospital clicks "🔒 Encrypt Record & Store to Cloud" (Two Parallel Paths):

[ HOSPITAL DATA OWNER ] ── Inputs: Patient ID, Diagnosis Plaintext, Keywords
PATH A: OFF-CHAIN CLOUD STORAGE
  1. Derives 256-bit AES key from collaborative token $\Phi$.
  2. Encrypts plaintext via AES-256-GCM.
  3. Generates 96-bit random Nonce + 128-bit GCM Tag.
  4. Computes keyword index $g^{\eta \cdot H_1(kw)} \bmod P$.
  5. Stores Heavy Payload in Cloud Storage.
PATH B: ON-CHAIN BLOCKCHAIN LEDGER
  1. Computes verification tag $y_k = g^{\sigma_k} \bmod P$.
  2. Sends transaction: registerDocument(docId, hash, y_k).
  3. Mines new Ethereum Block (e.g. Block #1045).
  4. Initializes deletedDocRegistry[docId] = false.
  5. Stores Immutable Tag & Status on Blockchain.

💡 Key Idea Features Implemented

🎲 Dynamic Random Clinical Case Generator

Auto-populates 10 realistic clinical specialties (Cardiology, Neurology, Oncology, Orthopedics, Pediatrics, etc.) with unique IDs and keywords upon upload.

⚡ Instant $\mathcal{O}(1)$ On-Chain Revocation

Blocks revoked files instantly on the Ethereum smart contract without re-encrypting the cloud database.

🛡️ Schnorr Zero-Knowledge Proof (SNIZK)

Mathematically proves that search results returned by the untrusted cloud are correct and complete without revealing file contents.
